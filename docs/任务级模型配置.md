# 任务级模型配置与真实调用留痕

适用范围：`enterprise/model_gateway.py`、`enterprise/model_registry.py`。2026-09-24增加全局受控模型选择与独立提供方配置；不是新模型实际调用成功、稳定性或多模型收益验收。未执行任何新增付费请求。

## 1. 默认行为与申报边界

- 未配置 `task_routing` 或 `enabled=false` 时，仍使用原有单模型配置与原环境变量优先级。原默认模型名仍为 `qwen-plus`，但**配置名不是实际响应证明**。
- 本实现不修改真实 `.local/llm.json`，不默认启用大模型、付费模型、新云端、自动升级或自动重试。服务端管理员审批、凭据与原外网授权边界仍然适用。
- 一个统一 HTTP 调用点是集中控制超时、并发与安全策略的设计，并不是缺陷。模型是否分工应看任务映射与**实际响应记录**，不能数 HTTP 调用点。
- LLM 任务路由与检索重排完全不同。`controlled-domain-lexical-reranker`、`neural=false` 仍应称为词法重排；本实现不会使其成为 bge-reranker 神经重排。
- 离线工具里出现 `qwen-max` 不等于在线业务调用了它。白名单路由已实现、未启用，不应宣称生产“四模型分工”。只有之后经授权取得真实调用证据，才可说明运行过哪些模型。

## 2. 设置页受控模型选择（2026-09-24）

设置页列出注册名称、请求模型、凭据状态、独立云授权、每次请求时限和最近实际调用耗时。需要 `system.read` 查看，`system.configure` 保存；选择范围是**当前整个部署的全部用户**，不是隐含的个人会话设置。只有保存后影响新的 `attribution`、`benchmark`、`report` 调用，其他任务继续原路由；历史快照不改写。未保存选择时保持 `legacy`，不自动从旧配置切换提供方。

|注册名称|默认模型|密钥环境变量|云授权环境变量|每次默认时限|
|---|---|---|---|---|
|legacy|原配置/任务路由|保持旧行为|保持旧行为|原配置，分析阶段最多40秒|
|qwen-plus|qwen-plus|DASHSCOPE_API_KEY|DASHSCOPE_APPROVED_CLOUD=true|40秒|
|qwen-turbo|qwen-turbo|DASHSCOPE_API_KEY|DASHSCOPE_APPROVED_CLOUD=true|40秒|
|deepseek|deepseek-flash|DEEPSEEK_API_KEY|DEEPSEEK_APPROVED_CLOUD=true|80秒|

DeepSeek当前API名称依据2026-09-24读取的[官方模型表](https://api-docs.deepseek.com/quick_start/pricing/)；`deepseek-chat`不当作当前模型名硬编码。部署运维可通过 `DEEPSEEK_MODEL` 或受控注册项指定已核实的ID。页面不得输入自由模型名、地址、密钥、预算或任意请求参数；注册配置只接受 `provider/model/timeout/base_url/approved_cloud`，支持的提供方为 `dashscope` 和 `deepseek`，HTTPS地址由运维控制。DeepSeek固定使用官方非思考JSON请求选项，不接收业务payload覆盖。地址、模型和时限的配置变更均需要独立评估和重新验收。

提供方密钥不互相回退：旧 `COST_LLM_API_KEY` 或本地旧密钥不会自动发送给新提供方。凭据未配置或服务端云授权未给出时，保存新选择失败，不会发起探测请求。环境值示例只是配置说明，不表示当前已批准上传业务数据；本轮没有写入真实服务配置或新授权。

新注册配置的可终止模型阶段预算为 `min(255, 2 × 每次请求时限 + 15)` 秒，单次请求仍受阶段剩余预算限制，最多首次加一次校验修正。时限须为1至120秒有限数值。80秒配置对应175秒阶段预算，40秒对应95秒；**不保证在此时间内返回或通过**。原未选择注册项的新版散文仍95秒、旧合同45秒，原40秒请求上限不变。父进程冻结安全配置身份，worker重新解析并比对；执行中配置不一致时拒绝，不静默换模型，密钥不进入worker请求JSON。

实际审计保存注册ID、请求模型、提供方返回模型（若有）、配置及请求摘要、时限、耗时和结果；别名不能证明精确权重版本，供应商未返回的版本保持未知。最近耗时仅来自同配置的真实请求记录，缺失时为空，不是估计速度，也不是五次稳定性。切换后需另行授权新模型的独立固定批次，失败记录保留，不能继承旧模型采用率或筛选重试结果。

## 3. 向后兼容接口

```python
configuration(task=None)
generate_json(instruction, data, *, max_tokens=2500, config=None, task=None)
provenance(instruction='', *, task=None, trace=None)
```

保留 `ModelConfiguration(base_url, model, api_key, approved_cloud, timeout)` 原五个位置参数。新增属性均有默认值，`dataclasses.replace(config, timeout=...)` 可继续使用。

`generate_json` 仍返回**精确的内置 `dict`**。不会添加 `_metadata` / `model` 等业务字段，也不使用 dict 子类，兼容现有 `type(candidate) is dict`、strict keys 与 JSON 序列化校验。

任务固定枚举：

| task | 用途 |
|---|---|
| `attribution` | 成本归因假设与建议 |
| `benchmark` | 工厂对标说明 |
| `report` | 报告叙事 |
| `task` | 整改任务建议草稿 |
| `agent_proposal` | 可选、受控的 Agent 结构化提议 |
| `summary` | 摘要 |

任务由业务调用点指定，不从用户 prompt 猜测。未知 task、任意 URL、对象、列表均拒绝，不把未知内容写入调用日志。

## 4. 原任务路由 profile 白名单

只从现有服务端配置文件中的 `task_routing` 读取。以下为**文档示例，不是已应用的配置**；示例使用占位模型并保持关闭，不提供密钥：

```json
{
  "task_routing": {
    "enabled": false,
    "profiles": {
      "small": {"model": "approved-small-model", "timeout": 20},
      "narrative": {"model": "approved-narrative-model", "timeout": 40}
    },
    "tasks": {
      "attribution": "small",
      "benchmark": "small",
      "report": "narrative",
      "task": "small",
      "agent_proposal": "small",
      "summary": "small"
    }
  }
}
```

启用必须由服务端管理员另行评审并显式设置 `enabled=true`；修改前应评估费用、数据授权、测试与回退方案。本轮不执行这些操作。

安全约束：

1. profile 名白名单来自配置文件的 `profiles` 键；任务只映射这些名字，保留名 `default` 指向原单模型。
2. 每个 profile 只允许 `model` 与可选 `timeout`，时限为 1—120 秒。`endpoint` / `base_url` / `api_key` / `approved_cloud` 等字段直接拒绝，不能借 profile 绕过原连接与外网授权。
3. 所有 profile 继承原服务端 endpoint、key 与 cloud approval；不能让用户提交任意模型名、profile、连接地址或凭据。
4. 旧 Python `config=` 保留为**服务端代码/测试注入**，只接受 `ModelConfiguration`，不接受用户 JSON dict。不得在 API 层将用户输入转换成任意 `ModelConfiguration`。
5. 显式配置须按相同任务解析：`configuration(task='report')` 与 `generate_json(..., task='report', config=config)`。启用路由后将无任务配置交给有任务调用，或任务不一致，均拒绝，避免静默绕过任务路由。
6. 设置页已移除旧密钥/地址输入、旧配置保存和连通性探测，仅允许选择注册名称。保留的旧 `save_local_configuration` 是兼容运维接口，不用于新模型选择；新 `save_selection` 仅原子合并选择ID，保留既有密钥、授权和任务路由，不调用模型。

### 路由决策记录

| routing_reason | 行为 | routing_fallback |
|---|---|---|
| `routing_disabled` | 默认未启用，沿用旧模型 | false |
| `task_unspecified` | 未指定任务，沿用旧模型 | false |
| `default_profile` | 明确映射到 default | false |
| `task_profile` | 命中服务端白名单 profile | false |
| `task_unmapped` | 路由启用但此任务没有映射，退回旧模型 | true |
| `profile_missing` | 引用的 profile 不存在，退回旧模型 | true |
| `explicit_configuration` | 旧服务端五参构造的显式配置 | false |
| `unresolved` | 调用前配置/参数失败，未解析成功 | false |

非法策略/字段/时限会失败关闭，不执行回退请求。供应商报错也不会重试、换 endpoint 或换更大模型。`routing_fallback` 仅是**发请求前的路由回退**，不是供应商故障切换，也不是业务规则草稿回退。

## 5. 真实响应留痕合同

```python
from enterprise.model_gateway import capture_model_calls, generate_json, provenance

with capture_model_calls() as calls:
    candidate = generate_json(instruction, data, task='report')

# candidate 仅含业务 JSON；metadata 另存到已有的审计/worker结果容器。
metadata = provenance(trace=calls[-1], task='report')
worker_result = {'candidate': candidate, 'model_calls': calls}
```

`calls` 为纯 JSON 可序列化的 `list[dict]`，不含 SDK 对象、连接、异常对象或自定义编码器依赖。嵌套 capture 的记录同时进入外层 scope，每层一次；独立线程/async scope 不使用全局“最后一次模型响应”，避免串单。调用完成后不继续追加旧 scope。

对于异常与多次受控纠正，应在真正执行调用的函数里记录每一次 attempt：

```python
with capture_model_calls() as calls:
    try:
        candidate = request_fn(instruction, data, config=config)
    finally:
        attempt['model_calls'] = calls
```

即使 `generate_json` 抛出 `ModelUnavailable`，`calls` 仍包含该次安全记录；该异常同时提供 `.metadata` 作为可选单记录通道。没有网关调用的注入函数产生空列表，应标记“注入/未观测”，不能重新读配置填充假响应。

**跨进程注意**：ContextVar 不是 IPC。必须在发请求的 worker 内打开 capture，并把 `model_calls` 放入既有 worker 结果/attempt 审计通道，父进程直接读取。仅在父进程 capture 不能捕获另一个进程的调用。新测试实际运行独立 Python 解释器，通过 JSON 文件完成记录往返；不要求修改现有 worker 协议实现。

### 字段来源与诚实边界

| 字段 | 来源与含义 |
|---|---|
| `schema`, `call_id`, `started_at` | 本次客户端调用的记录版本、随机关联 ID、UTC 开始时间 |
| `provider` | 固定 `openai_compatible`，表示适配协议，不猜测云厂商身份 |
| `requested_model` | **发出的请求参数**；不得代替实际返回 model |
| `model` | **此响应对象的 `response.model`**；缺失或不安全时为 null，不读配置补造 |
| `request_id` | SDK `_request_id` 优先；若无则保留 `response.id` 并标明来源；两者都无则 null |
| `request_id_source` | `http_request_id` / `response_id` / `http_error_request_id` / `unreported`，不混称 HTTP 请求 ID 与 completion ID |
| `completion_id` | `response.id` 单列，便于与供应商请求号区分 |
| `usage` | 供应商真实返回的已知非负整数 token 统计；支持 SDK 对象/字典与 token details；缺失为 null，非数值/任意扩展字段不收录 |
| `task`, `profile`, `routing_*` | 此调用实际采用的服务端路由决策，不是调用后重读的配置 |
| `duration_seconds` | monotonic 计算的端到端耗时，含配置、排队、网络及 JSON 校验；不宣称纯供应商推理时长 |
| `request_attempted` | 是否已经进入 SDK create 调用；不保证远端已收到或执行 |
| `response_observed` | 是否实际获得 completion 响应对象；JSON 无效时也可能为 true |
| `source` | `not_called` / `request_attempt` / `provider_response` |
| `status` | `returned_json` / `invalid_response` / `unavailable`；网关 JSON 有效不代表业务 schema 已通过 |
| `failure_type` | 异常类型，不写供应商错误原文 |
| `prompt_sha256`, `request_sha256`, `response_sha256` | 输入指令、请求内容、返回文本的哈希；非完整业务内容 |

敏感信息约束：调用 trace 不写 endpoint、key、headers、完整 prompt、输入业务数据、完整响应或异常正文。`api_key` 不出现在配置对象 repr 中；对模型名/ID等标识符限制长度与字符集并拦截当前密钥回显；usage 仅取白名单数值字段。

`provenance(instruction)` 保留旧签名与原字段供**配置预检**：其中 `model` 是配置名，另带 `requested_model`、`source='configured_only'`、`response_observed=false`、`request_attempted=false`。预检不能当作完成调用证据。实际审计必须使用 `provenance(trace=...)` 或直接保存 capture 记录；该路径不重新读取配置。

## 6. 业务接入分工（原任务路由参考）

| 调用点 | 应接任务 | 应保存记录的位置 |
|---|---|---|
| `attribution_gen._llm_generate` | `attribution` | 每次初始/纠正 attempt 独立 `model_calls` |
| `enterprise.benchmark_ai._llm_generate` | `benchmark` | 每次初始/纠正 attempt 独立 `model_calls` |
| `enterprise.analysis_service` 报告生成 | `report` | 实际报告 worker 内捕获并随结果序列化 |
| `enterprise.task_workflow._default_llm` / `generate` | `task` | 调用后 `generation.model_calls` / 实际 provenance；不可沿用调用前配置推断 |
| 可选 Agent proposal 调用 | `agent_proposal` | 提议记录中；无调用时不得有伪造的响应身份 |

目前归因/对标使用 `type(candidate) is dict`，所以本实现不强迫业务修改 strict keys 校验。业务调整时对注入 `request_fn` 的旧签名应单独兼容，不应把新的 task 参数强塞给所有测试钩子。
